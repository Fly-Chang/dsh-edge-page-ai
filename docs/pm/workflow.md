# 05 开发与协作流程

- 文档编号: PM-05
- 版本: 1.0.0
- 状态: 生效
- 生效日期: 2026-08-16

## 1. 总体流程

```text
需求/想法 → 记录到项目章程或问题区 → 任务分解 → 实现 → 测试 → 工作日志 → 提交 → 变更日志
```

## 2. 分支与提交

1. 主分支 `main` 永远保持可运行。
2. 功能分支命名：`feature/<slug>`；修复分支：`fix/BUG-NNN-<slug>`；文档分支：`docs/<slug>`。
3. 提交信息格式：

```text
<type>(<scope>): <一句话说明>

- 关联: BUG-NNN / 无
- 测试: 通过 / 未执行（原因）
```

`type` 取值：`feat`、`fix`、`docs`、`test`、`chore`、`refactor`。

## 3. 任务粒度

1. 每个任务应在半个工作日内可完成；超过则继续拆分。
2. 任务产出必须落到具体文件，并写入当日工作日志。

## 4. 缺陷处理流程

1. 发现缺陷立即在 `docs/bugs/` 新建 `BUG-NNN.md`（模板见 PM-04）。
2. 在工作日志“问题与阻塞”中登记该缺陷编号。
3. 修复分支名含 `BUG-NNN`；提交信息关联 `BUG-NNN`。
4. 修复后运行相关测试，并在缺陷文件“验证记录”登记结果。
5. 验证通过后状态置为 `closed`，并在 `CHANGELOG.md` 的 `Fixed` 下登记。

## 5. 质量门槛（合并前检查）

- [ ] `npm test` 全部通过。
- [ ] 新增/修改文件命名符合 PM-02。
- [ ] 当日工作日志已填写。
- [ ] 缺陷与变更日志已同步。
- [ ] 无密钥、日志、构建产物进入提交。

## 6. 发布与版本

1. 版本号遵循 `MAJOR.MINOR.PATCH`。
2. 协议破坏性变更 → MAJOR；向后兼容的新能力 → MINOR；修复 → PATCH。
3. 每次版本发布必须更新 `CHANGELOG.md`，格式见该文件顶部说明。
